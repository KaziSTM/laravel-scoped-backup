# Security & Threat Mitigation

Backups contain complete replicas of your database and files. This document details the security model, threat mitigations, and best practices implemented in `kazistm/laravel-scoped-backup`.

---

## 1. Credential Security

Database credentials (passwords, usernames, hosts) must never leak into command lines, process tables, or log files.

- **Environment-Only Credential Injection:**
  - **PostgreSQL:** Passwords are fed via the `PGPASSWORD` process environment variable.
  - **MySQL / MariaDB:** Passwords are fed via the `MYSQL_PWD` process environment variable.
  - Credentials are **never** passed as CLI arguments (`-p<password>`), preventing them from appearing in system process lists (`ps aux`, `/proc/<pid>/cmdline`).
- **Command-Line Array Construction:**
  Processes are spawned using explicit argument arrays (`new Process(['pg_dump', ...])`), preventing shell string interpolation and command injection attacks.
- **Log Redaction:**
  Process error outputs and exception messages are automatically sanitized using `sanitizeOutput()`, replacing detected passwords with `[REDACTED]`.

---

## 2. Archive Security & Extraction Protections

When extracting archives during restoration, `ArchiveManager` enforces strict defenses:

### Zip Slip Protection (Directory Traversal)
- Every entry path inside the ZIP is checked before extraction. Any entry containing `..`, leading slashes (`/`, `\`), or relative references is rejected immediately with a `SecurityException`.
- Canonical destination verification: The resolved target directory of each entry is checked with `realpath()` to ensure it strictly resides within the target extraction root directory.

### Zip Bomb Protection
- `ArchiveManager` tracks cumulative uncompressed bytes during the validation pass. If the extracted size exceeds the maximum limit (`MAX_UNCOMPRESSED_BYTES = 5368709120` bytes / 5 GB), extraction is aborted to prevent storage denial-of-service.

### Symlink Rejection
- When packaging files into full backup archives, symbolic links are skipped to avoid traversing into sensitive external host paths (e.g. `/etc`, `/proc`).

---

## 3. Temporary Staging Directory Security

- Staging directories (`storage/framework/cache/backups`) are created with restrictive permissions (`0700` / read-write-execute only by the current process owner).
- This prevents unprivileged local users or container co-tenants on shared hosts from reading raw uncompressed dumps during backup or restore operations.

---

## 4. Production Restore Protections

Destructive full database restorations are protected by environment gates:

- If `app.env` is `production`, full restores are blocked unless `--force` is explicitly provided or confirmed via interactive prompt.
- For maximum safety, perform recovery drills into isolated databases using `--connection=recovery_db` rather than restoring into active production databases.

---

## 5. Encryption at Rest & in Transit

> [!IMPORTANT]
> **Encryption Status:**
> - Archives generated by `kazistm/laravel-scoped-backup` are standard, unencrypted ZIP files containing raw database dumps and JSONL streams.
> - The package currently does not encrypt archive contents with a symmetric password by default.

### Recommended Production Encryption Strategy
1. **Server-Side Storage Encryption:**
   When using cloud object storage (Amazon S3, Google Cloud Storage, Cloudflare R2), enable default server-side encryption with customer-managed or KMS keys (e.g. AWS KMS SSE-KMS).
2. **Encrypted Transport:**
   Always use HTTPS/TLS endpoints for remote storage disks.
3. **Encrypted Filesystems:**
   Ensure local disks or temporary volumes reside on encrypted filesystems (e.g. LUKS, dm-crypt).

If you discover a security vulnerability in `kazistm/laravel-scoped-backup`, please do **not** open a public issue on GitHub.

Instead, report the issue directly to the maintainer via email:
